# Wujin 2.0.2 Restore Session and CDK Error Mapping

## Scope

Add a reversible paid one-click configuration session and make Keygate CDK
failures actionable. The restore operation reverses only the paid workflow:
client rule/MCP files and the paid `reverse-skill` tree. It never removes the
separately managed `free-skills` tree or its ownership state.

## Goals

- Let a user restore a completed paid one-click configuration from the result
  page, including files that did not exist before configuration.
- Keep the restore session across application restarts.
- Refuse to overwrite files or directories that the user changed after the
  paid configuration; report those conflicts with their paths.
- Preserve the existing atomic-write and configuration lock guarantees.
- Map structured Keygate error codes consistently for HTTP 200 and non-200
  responses without exposing raw CDK values or server messages.

## Non-goals

- Do not restore or delete free Skill installations.
- Do not add retry policy, alternate domains, or server-side license changes.
- Do not infer a restore from content markers alone.

## Restore Session Model

Before `configure_selected` deploys anything, the backend creates one session
under the app-owned backup root:

```text
<backup-root>/configuration-sessions/<session-id>/
  manifest.json
  files/<stable-file-id>.snapshot
  skill-root/                    # present only when reverse-skill existed
```

The manifest contains the app version, selected client IDs, canonical target
paths, whether each target existed, the original SHA-256, and the post-success
SHA-256. The skill-root record contains existence, recursive tree hash, and the
snapshot path. All paths are validated under the user profile or backup root;
reparse points and symlinks are rejected.

The manifest is atomically written before deployment. A single active session
is stored in application state and can be recovered from disk after restart.
The session is marked `ready` only after configuration results are complete and
post-write hashes have been recorded.

## Restore Flow

1. The result page enables `还原完整环境` only for a ready paid session.
2. A confirmation dialog states that paid configuration and `reverse-skill`
   will be restored while free modules remain unchanged.
3. The backend acquires `configuration_write_lock` and loads/verifies the
   active manifest.
4. Every target is checked against its recorded post-success hash. A mismatch
   becomes a restore conflict and is left untouched.
5. Matching targets are restored atomically from snapshots; targets that were
   newly created are removed only when their current hash matches the recorded
   post-success hash.
6. The paid skill root is restored from its snapshot, or removed when it did
   not exist before the session, with the same post-state conflict check.
7. The manifest is marked `restored`, paid results are cleared, and a structured
   restore summary is returned. Failed/conflicted sessions remain on disk for a
   retry and retain evidence.

The operation is idempotent after a successful restore and never touches
`<local-app-data>/无限破甲/free-skills`.

## CDK Error Contract

The Keygate response parser reads `error.code` for every HTTP status and for
`success: false` envelopes returned with HTTP 200. Canonical mappings include:

- `INVALID_CDK`, `INVALID_LICENSE_KEY` -> `invalid_cdk`
- `UNISSUED_CDK`, `UNISSUED_LICENSE` -> `unissued_cdk`
- `DEVICE_ALREADY_BOUND`, `DEVICE_BOUND` -> `device_already_bound`
- `LICENSE_NOT_FOUND` -> `license_not_found`
- expiry, revoke, suspension, activation-limit, lockout, and retry-later
  aliases already defined by the product contract.

The UI maps canonical codes to customer-facing Chinese messages. Unknown codes
and malformed responses use a retryable generic message and a stable diagnostic
code in runtime logs; raw response text and CDK values are never logged or
shown.

## Verification

- Core restore tests cover existing targets, newly created targets, skill-root
  absent/present snapshots, user modifications, path traversal, tampered
  snapshots, idempotence, and free-tree preservation.
- Tauri tests cover session creation/recovery, command registration, lock and
  state clearing, and restore conflict summaries.
- UI tests cover the result-page confirmation, busy/error states, and the free
  module preservation copy.
- Online activation tests cover HTTP 200 error envelopes and all new aliases.
- The complete 2.0.2 automated gate runs before the production package build.
