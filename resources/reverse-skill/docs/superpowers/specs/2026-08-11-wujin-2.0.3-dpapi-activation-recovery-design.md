# Wujin 2.0.3 DPAPI Activation Recovery

## Evidence and Root Cause

Affected Windows installations can reach the production Keygate health and
public-key endpoints, have correct clocks, can use CurrentUser DPAPI for new
data, and can write the local license directory. Their existing
`device-identity.dpapi`, however, fails CurrentUser DPAPI unprotection while a
signed, unexpired `receipt.json` remains present.

The 2.0.2 startup path converts every device identity initialization error to
`None`. Activation then reports only that online authorization is unavailable,
which the UI reduces to the generic CDK verification failure. The failure is
local identity loss, not an invalid CDK or a Keygate outage.

## Goals

- Recover activation when the current Windows profile cannot decrypt the
  existing Wujin device identity.
- Preserve the one-CDK-to-one-device invariant: recovery replaces the old
  Keygate activation and never consumes a second activation slot.
- Require both a locally stored Keygate-signed receipt and the user entering a
  valid CDK before an old binding can be replaced.
- Keep the old encrypted identity and receipt as app-owned recovery evidence;
  never log or display the CDK, receipt token, seed, or private key material.
- Surface local identity and recovery failures as stable, actionable errors
  instead of a generic verification failure.

## Non-goals

- Do not change the seven-day signed offline receipt window.
- Do not add hardware fingerprinting or identify a machine from Windows
  hardware properties.
- Do not automatically move a CDK when no valid signed receipt exists.
- Do not add activation slots, weaken Keygate activation limits, or modify
  update behavior.
- Do not package or publish a release without a separate explicit owner
  instruction to produce a package.

## Approaches Considered

### 1. Signed local recovery using the existing deactivate endpoint (selected)

Verify the old receipt with the embedded Keygate receipt public key, recover
only its signed device identifier, stage a new DPAPI identity, deactivate the
old identifier with the user-entered CDK, promote the new identity, and
activate it. Keygate has zero or one binding throughout the transition.

This reuses the deployed API, limits production risk, and gives the client a
deterministic test seam. The transition is retryable because a missing old
binding and an invalid CDK both remain non-authorizing: the following activate
request is still required to succeed before the application becomes active.

### 2. New atomic Keygate rebind endpoint

Add a server endpoint that verifies an old receipt and swaps activation rows in
one database transaction. This gives stronger cross-network atomicity but
requires a new public protocol, server deployment, database integration tests,
and rollout coordination. It is unnecessary while the existing deactivate
and activate calls can preserve the single-binding invariant.

### 3. Delete local state and require an administrator reset

Quarantine the unreadable local identity and ask support to clear the Keygate
binding. This is simple but does not repair the customer workflow and creates
manual operational work for every Windows profile or DPAPI reset.

## Recovery Eligibility

Startup classifies online activation into three states:

- `ready`: the existing identity decrypts and the normal service initializes.
- `recoverable`: identity initialization failed, but `receipt.json` contains a
  canonical Keygate token whose Ed25519 signature, product ID, device ID, and
  fingerprint are valid.
- `unavailable`: no receipt exists, the receipt is malformed/forged/wrong
  product, or online service construction failed for another reason.

Receipt recovery verification does not grant authorization. It only returns
the signed old device identifier. An expired token may identify the old
binding, but Keygate still validates the entered CDK and current license state
before any new activation succeeds.

Startup performs no file mutation and no network request while classifying the
state.

## Recovery Flow

When the user submits a CDK in `recoverable` state:

1. Normalize the CDK without logging it.
2. Create and DPAPI-round-trip a staged replacement identity.
3. Copy the unreadable identity and old receipt into an app-owned timestamped
   recovery directory under the license root. Backups never contain plaintext
   CDK material.
4. Call the existing Keygate `/license/deactivate` route with the entered CDK
   and the old signed device identifier.
5. Treat a successful deactivation as completion. Keygate intentionally uses
   the same `license_not_found` response for a wrong CDK and a missing binding,
   so that response alone is not safe to treat as idempotent success. Re-run
   activate then deactivate against the old signed identifier; only those
   server-authorized calls allow local identity replacement to continue.
6. Atomically promote the staged DPAPI identity to
   `device-identity.dpapi`, initialize the normal online activation service,
   and call `/license/activate` with the new identifier.
7. Only a verified, saved new receipt changes application authorization to
   active. Store the new service in runtime state for refresh and future
   activation calls.

If the network fails before deactivation, local primary files remain unchanged.
If activation fails after deactivation, the new identity remains stable and a
normal retry can recreate the sole Keygate binding. The old receipt may remain
as backup evidence but cannot refresh against the removed binding and naturally
expires within its original offline window.

## Component Changes

- `wujin-core/online_activation`: add typed deactivate request support and a
  recovery-only signed receipt reader that exposes only the old device ID.
- `wujin-windows/device_identity`: add staged replacement and atomic promotion
  with backup behavior; never silently delete an unreadable identity.
- Tauri application state: retain `ready`, `recoverable`, or `unavailable`
  initialization evidence instead of discarding all errors with `.ok()?`.
- Activation command: route only eligible recovery through deactivate,
  identity promotion, and normal activation; keep locks out of blocking HTTP
  operations and serialize activation recovery.
- UI error mapping: add stable messages for unrecoverable local identity,
  recovery storage failure, and retryable recovery network failure.

## Security Invariants

- The embedded receipt public key verifies recovery evidence; no signing key is
  added to the client.
- A receipt alone cannot activate. The user-entered CDK must authorize both the
  old deactivation and the new activation.
- A `license_not_found` deactivation cannot replace local identity by itself;
  the old identifier must first pass a same-CDK activate/deactivate round trip.
- Server activation count never exceeds one during recovery.
- Old offline receipts cannot refresh after their server binding is removed;
  they may remain usable only for their already-issued, at-most-seven-day
  signed window.
- Recovery files remain under the app-owned local license root and are never
  scanned as active receipts.
- Raw HTTP bodies, CDKs, receipt tokens, DPAPI blobs, and identity seeds never
  enter logs, UI errors, tests, or committed fixtures.

## Error Contract

- `activation_identity_unavailable`: identity cannot be decrypted and no valid
  signed recovery receipt exists.
- `activation_recovery_storage_failed`: staging, backup, or promotion failed;
  the user can retry after fixing local storage.
- Existing `license_api:*` errors remain authoritative for CDK and service
  decisions.
- Transport failure before or during recovery remains retryable and never marks
  the application active.

## Verification

- Core tests watch forged, malformed, wrong-product, wrong-fingerprint and
  valid/expired signed recovery receipts get rejected or accepted as designed.
- HTTP contract tests prove `/license/deactivate` request shape, response
  parsing, error mapping, and no CDK leakage.
- Windows tests reproduce a DPAPI blob encrypted outside the current user
  context (or a deterministic injected unprotect failure), then prove staging,
  backup, promotion, and retry behavior without deleting owner data.
- Tauri tests reproduce 2.0.2's swallowed initialization failure and prove the
  new recoverable state performs deactivate before activate, ends with one
  ready service, and never grants access on partial failure.
- UI tests cover all new stable errors and retain the generic fallback for
  unknown failures.
- Run targeted Rust/UI tests, workspace format/clippy/tests, the applicable CDK
  verification matrix, and the full non-packaging gate. Launch the debug client
  for owner acceptance. Packaging remains locked until the owner explicitly
  requests it.
