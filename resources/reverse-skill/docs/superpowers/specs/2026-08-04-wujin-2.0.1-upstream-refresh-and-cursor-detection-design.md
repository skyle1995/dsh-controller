# Wujin 2.0.1 Upstream Refresh And Cursor Detection Design

## Goal

Produce a Windows `2.0.1` formal release candidate that refreshes the paid and free embedded projects with real upstream content changes and fixes detection of an official Cursor installation located outside the default system drive.

This release preserves the existing paid/free bundle isolation, CDK and receipt trust boundaries, update-signing boundary, user configuration files, and unrelated worktree content.

## Cursor Detection

### Problem

The current Cursor adapter only probes manifests below `%USERPROFILE%\AppData\Local\Programs\cursor`. An official installation placed on another drive is therefore reported as missing even though `Cursor.exe` is installed and usable.

### Architecture

Windows-specific discovery belongs in `wujin-windows`; manifest parsing and client configuration remain in `wujin-core`.

1. A Cursor install resolver reads candidate locations from the current-user and local-machine Windows registration surfaces used by the official installer:
   - `App Paths\Cursor.exe`.
   - `Uninstall` entries whose product identity is Cursor, including 32-bit and 64-bit registry views.
2. The resolver extracts paths only from structured values such as `InstallLocation`, `DisplayIcon`, and the registered executable path. Quoted executable arguments are parsed without executing them.
3. Standard per-user and `Program Files` locations remain fallback candidates for missing or incomplete registry data.
4. Every candidate must resolve to an existing `Cursor.exe`. Its adjacent `resources\app\package.json` or `resources\app\product.json` must also exist before it is passed to the core adapter.
5. Candidates are normalized and deduplicated. Stale, malformed, unrelated, or inaccessible registry entries are skipped without failing detection of other clients.
6. `AppState::service` supplies the resolved Cursor manifests to a new registry construction path. Existing tests and non-Windows core callers retain the current default constructor and deterministic path behavior.

Drive letters are never hard-coded and fixed drives are not recursively scanned. The existing configuration targets under `%USERPROFILE%\.cursor` remain unchanged.

### Detection Result

- A valid official installation on any drive is `detected = true`.
- The version is read from the first valid manifest using the existing version-gated behavior.
- A manifest without a readable version remains detected but unverified, preserving the existing opt-in write behavior.
- If all candidates are invalid or absent, the current missing-client result is returned and no configuration files are written.

## Version Contract

All customer-visible and build-enforced version surfaces move from `2.0.0` to `2.0.1`, including Rust/Tauri package metadata, frontend metadata, PE resources, bundle configuration, release scripts, artifact naming, and version consistency tests.

The production build approval token must name `2.0.1`; the old `2.0.0` token must fail. Existing CDK, legacy CDK, receipt, and update public-key separation remains unchanged. No signing private key, issued CDK inventory, or release secret may enter the repository or customer package.

## Error Handling

- Registry access failure is a recoverable discovery miss, not an application failure.
- A stale registered path is ignored and fallback discovery continues.
- Invalid Cursor JSON uses the existing client-manifest error path and does not write rules or MCP configuration.
- Upstream synchronization stops if a source commit, license, expected tree, catalog, SBOM, or embedded archive does not agree.
- Release construction stops on any failed test, secret scan, PE/resource check, signature check, or artifact integrity check.

## Verification

Implementation starts with failing tests and must cover:

- Official Cursor installed under a non-C drive registry path.
- Current per-user default install path.
- App Paths and Uninstall discovery, including quoted `DisplayIcon` values.
- Deduplication when multiple registry surfaces point to the same installation.
- Stale, malformed, unrelated, and missing registry entries.
- Existing Cursor manifest parsing, unverified-version behavior, configuration writes, and no-write-on-miss behavior.
- Paid GPT v42 source/payload/hash verification.
- NERV source evidence and runtime-payload equivalence.
- Updated free Skill tree, license, catalog, SBOM, notices, and archive verification.
- Full Rust, frontend, Tauri, paid/free isolation, activation, update, build-key, secret-scan, and release gates.
- Release EXE version/resource inspection, SHA-256, size, PE validity, and expected Authenticode publisher verification.

The final report records the exact source commits, test commands, artifact path, size, SHA-256, PE version, and Authenticode result.

## Publication Boundary

The requested output is a local formal `2.0.1` package for owner testing. Building the package does not publish or replace the production update manifest, website download links, GitHub release, or public mirror. Those cutovers require a separate explicit publication instruction after owner acceptance.

## Acceptance Criteria

- An official Cursor installation outside the C drive is detected without scanning every drive or requiring manual path selection.
- Paid and free embedded content matches the approved upstream scope and remains isolated.
- Every version surface reports `2.0.1`, and the old production approval token is rejected.
- All applicable automated gates pass from the release commit.
- The produced formal package contains no private keys, CDK inventories, release secrets, temporary payloads, or unrelated worktree files.
- The package passes PE/resource, integrity, and Authenticode publisher checks and is ready for owner testing without changing public distribution state.
